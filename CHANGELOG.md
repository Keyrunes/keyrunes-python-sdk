## [0.4.0] - 2026-09-15

### Added

- **client**: change_password, which the API served and the SDK did not expose

  `POST /api/user/change-password` has been in Keyrunes all along. The SDK exposed
  `login`, `refresh_token`, `register_user` and the group queries — and not this
  one.

  Whoever needed it built the HTTP call by hand: that is what happened downstream
  in PlayfulLMS, and before that the conclusion was worse — reading only the SDK's
  surface, the operation was written off as nonexistent, and the platform nearly
  told people to change their password at the provider instead.

  **Details that cost you if read wrong**

  `/api/user/change-password`, and **not** `/api/change-password`: the router
  registers the first. The handler behind the second is dead code marked
  `#[allow(dead_code)]`, and pointing at it answers 404.

  The server answers errors as **plain text** (`e.to_string()`), not JSON — treat
  it as JSON and you get a parsing exception instead of the sentence explaining
  what went wrong.

  The error is **400**, not 401, which is why it becomes `NetworkError`: that is
  the class this SDK already uses for everything that is not 401/403/404. Changing
  it here would change the contract for every caller because of one endpoint. The
  server's wording survives, which is what matters — "invalid current password"
  and "password too short" call for opposite fixes.

  Without a token it refuses **before** sending: the server decides whose password
  it is from the token, and nothing in the body chooses that.

  And the effect that closes the loop: the server clears `first_login` on a
  change — the origin of the `requires_password_change` the login reports. It is
  in the docstring because callers need to know there is no second call to make.

  Verified against a real Keyrunes, not only against a double: register, change,
  and then the old password refused (401) and the new one accepted (200), with
  `first_login` cleared.

### Fixed

- **client**: contain a malformed `groups` instead of taking the client down

  The repository's own fuzz suite found it: with `{"groups": true}` in the server
  response, normalization raised
  `TypeError: argument of type 'bool' is not a container or iterable`.

  `data.get("groups", []) or []` handles null and empty, and **nothing else**:
  `True or []` is `True`, which survives all the way to the `"admins" in groups`
  just below.

  A client that falls over on a malformed response is worse than one that ignores
  it: whoever consumes the SDK sees a type error coming from inside the library,
  far from the cause, and nothing points at the server as the origin.

  Pre-existing — `git stash` and the failure stays. Detection measured: putting
  the `or []` back fails the fuzz test.

- **deps**: pyjwt 2.10.1 → 2.14.0 and idna 3.11 → 3.19 (OSV advisories)

  The `safety` hook does not run on this machine — it asks for an interactive
  login and dies with `EOF when reading a line`. Rather than skip the security
  check and move on, the 90 versions pinned in `poetry.lock` were run against the
  OSV database.

  Two findings in the runtime tree:

  - `pyjwt` 2.10.1: nine advisories, four of them high severity. In an
    authentication library this is the dependency that matters most. Fixed in
    2.13.0; `pyproject` already declared `^2.9.0`, so no API changes — only the
    lock.
  - `idna` 3.11: two moderate advisories, fixed in 3.15. Arrives through `httpx`.

  After the update the runtime tree carries no known advisory. The 194 tests pass
  unchanged.

  What remains are advisories in the development tree — `authlib`, `nltk`,
  `cryptography`, `requests`, `urllib3` — and it is worth saying where they come
  from: **every one of them is a dependency of `safety` itself**. The scanner that
  cannot run is also the largest source of vulnerable packages in the environment.
  They are left alone: they are development-only, they do not ship in the
  published package, and resolving it means deciding whether `safety` stays.

  The `v0.4.0` tag sat on `chore(release): 0.4.0`, and two commits went in after

  **not published** (the remote does not have it), the fix can still go into 0.4.0

- **changelog**: generate CHANGELOG.md with git-cliff, commit body included

  The changelog in this repository was written by hand. The first attempt at
  switching to generation was measured and **thrown away**: with git-cliff's
  default template, which uses only the subject line, the file dropped from 246 to
  61 lines — the "what" survived and the "why" disappeared.

  What fixes it is including the commit **body**. The messages here already
  explain the decision, so the information was never only in the changelog: it was
  duplicated. The generated file now runs to 222 lines, and every entry carries
  the text that explains it.

  Three details in `cliff.toml`, each from a defect visible in the output:

  - `indent(prefix="  ", first=true, blank=false)` on the body. Without
    `first=true` the body's first line falls outside the list item; with
    `blank=true` the empty lines pick up two spaces and the `trailing-whitespace`
    hook fails the commit.
  - A postprocessor demotes to bold any `#` heading arriving inside a body —
    indented, ATX is still a heading (it allows up to three leading spaces) and
    would collide with the changelog's own levels. The pattern uses `[ \t]` and
    **not** `\s`: `\s` matches `\n`, and in the first version it reached across
    the line break and ate the changelog's own `## [0.4.0]`, which turned bold.
  - Another postprocessor puts a blank line before each `## [version]`, because
    `trim = true` glues the heading to the last line of the previous release.

  Two sections shrink, and it is worth naming them: **0.1.0** (81 → 7 lines) was
  an inventory of the API — the same thing the README already carries — and
  **0.3.0** (55 → 11) loses the detail of the four contract bugs, because that
  release's commit has a short body. The old text stays recoverable in git
  history. From here the rule is different: the commit body is the source, so a
  thin message makes a thin entry.

  Along with it:

  - `task changelog` generates and `task changelog-check` fails when the file is
    out of date with the commits (a CI gate).
  - `NEWS.rst` goes. It was a third changelog, in the format towncrier would
    produce, with nothing generating it and nothing referencing it — a dead file
    for the same reason towncrier left in the previous commit.

  One honest caveat: that commit's body ends by saying "the changelog in this
  repository is written by hand". It was true when written and stopped being true
  now; a changelog is a historical record, and rewording the message to hide that
  would cost rewriting already-published history.

### Maintenance

- **deps**: drop towncrier, declared and never configured

  `towncrier` had been a dev dependency from before, **without a
  `[tool.towncrier]` section** in `pyproject.toml`, without a `towncrier.toml` and
  without a fragments directory. Running it fails: "the config file does not
  contain 'version' or 'package'".

  `NEWS.rst` is in the format it *would* produce, which is worse than having
  nothing: whoever arrives concludes the file is generated and leaves it alone, or
  tries to run the tool and finds out it cannot. That happened here today — the
  changelog was written by hand without noticing there was a tool declared.

  A declared, unused dependency is the same family as dead code. The changelog in
  this repository is written by hand, and now `pyproject.toml` says so.

## [0.2.0] - 2026-09-03

### Added

- **tests**: add property-based, fuzz and contract suites; release 0.2.0

  Add three new test suites and the tooling to measure them:

  - tests/test_property_based.py (24 tests): Hypothesis invariants over base
    URL normalization, _normalize_user id precedence and is_admin derivation,
    JWT claim parsing, request URL construction, status-to-exception mapping
    and model validation bounds.
  - tests/test_fuzz.py (19 tests): hostile-input crawl of the public surface
    asserting only KeyrunesError and pydantic ValidationError ever escape.
  - tests/test_request_contract.py (33 tests): mocks only the httpx transport
    so the method, URL, headers and JSON body put on the wire are asserted.

  Hypothesis profiles (fast/dev/ci) are selected with HYPOTHESIS_PROFILE;
  fast is derandomized and database-free so mutmut judges every mutant
  against identical examples.

  Two defects the new suites uncovered are fixed:

  - A 2xx response with a non-JSON body raised a raw ValueError out of
    _make_request. It is now wrapped in NetworkError.
  - get_user, get_current_user and has_group carried unreachable
    "except UserNotFoundError" fallbacks that re-tested a condition already
    forced by an early return, swallowing genuine server 404s. Removed, and
    the duplicated claims-to-User block extracted into
    _user_from_token_claims().
